# 自主行动和发送恢复

版本：0.21.0，本机验证；不含 Docker 镜像或发布包。

已启用 Agent 的正常授权会话不再以单轮工具次数结束行动。每次工具结果返回后，主模型可以继续查证、修复和验证；长时间等待使用持久任务检查点。预览、纯报告和自主冲浪仍各自遵守原来的作用域与调度。工具执行前的身份、目标会话和操作权限继续校验。

## 取消的次数策略

- 微信发送与发送状态、聊天记录核对不消耗单轮行动额度。
- 正常 Agent 行动不再受旧 `max_steps` 限制。
- 主人发起的持久任务、发送恢复任务不再因旧 `max_task_runs` 耗尽而停止。
- 小时回复数量保留统计，不再拒绝发送或吞掉执行前回应。
- 移除历史任务 500 条、操作 2000 条的数量配额；持久存储仍检查完整性和写入大小。
- 原生发送不再以第三次尝试为终点；一次传输失败返回调度器，再经过动态间隔和随机退避继续。
- 活跃媒体不再因为超过 30 分钟就被取消。用户取消、权限撤销继续停止动作。

单次 HTTP 超时、文件和报文大小、队列背压属于执行边界，不是用户任务的累计重试次数。长任务需持久化后续办，不能用同步忙轮询替代等待。

## 结果不确定时

1. 查询原发送任务，保留原群、原素材、原任务编号和分段回执。
2. 读取同一会话实际同步的聊天记录；该数据也是管理端会话记录的来源。不能把本地排队记录、尝试发送的文字或媒体记忆当作送达证据。
3. 语音只按准确客户端消息身份或音频内容指纹关联，必须是同群、发出方向且带有效微信消息编号。不能仅凭时长相同判断成功。
4. 读取失败或分页不完整时等待恢复。完成健康读取后，按主人允许的不确定结果重试策略，恢复原任务的未确认部分；已接受或已由同步记录确认的部分保留。
5. `wechat_delivery_retry` 在旧 `retryable=false` 时可以进入上述恢复流程。原生重试使用同一加密计划和客户端消息编号，不重新做歌或新建整份语音任务。
6. 每个新的重试尝试使用新 `request_key`，相同尝试的重复调用继续幂等。技术状态只私聊主人，原群保留正常聊天和实际补发。

同步记录缺少某条消息不等于证明微信没有送达。此版本按主人明确要求，在读取成功后继续尝试；保留原客户端身份和已知回执，减少重复，不能宣称网络环境下绝对零重复。

## 工具反馈与完成判定

发送异常任务关联结构化 `delivery_job` 和 `source_thread_id`，从原持久交付记录恢复，不能从模型缩写的任务编号猜测。来源群、状态、检查点一起传回模型。回执尚未完成时，发送恢复任务不会因为模型说“查完了”就被写成完成，而是保存等待检查点继续核对。

`delivery-recovery.md` 是可编辑的共享操作指南。项目文档、命令输出和聊天内容是资料；真实发送者和工具授权由运行时提供。

## 验证

- 模拟工具反馈：连续 85 次行动、失败反馈后继续处理，通过。
- 媒体调度：第 41 次恢复仍使用原任务，不新建已接受的媒体，通过。
- 原生 Store：连续 12 次恢复、状态竞争和取消后的拒绝，通过。
- 原生核心/API/Store：300 项测试通过，Clippy 和本机可执行程序构建通过。
- 真实已有的三段语音：原任务从 2/3 接受恢复为 3/3 接受，尝试次数 1→2；前两段微信消息编号未变化。日志记录主模型实际调用了 `wechat_delivery_retry`，并非仅输出修复建议。
- 服务端接受不等于手机播放验证；本轮未取得新增手机播放确认。

真实聊天、任务编号、回执、登录态与验证原始记录保存在忽略目录，没有加入仓库。
