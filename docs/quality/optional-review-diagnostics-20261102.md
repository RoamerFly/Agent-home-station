# 默认关闭额外模型复核与失败诊断（2026-11-02）

## 本轮核对结果

最新一次群内前序视频总结确实没有发送。回合状态为 `initial_check_failed`，界面“需处理”表示本回合需要处理失败原因，不表示仍在自动排队。之后另一个主动评估回合的安静结果不能代表这个总结任务已恢复。

保存快照中的复核输入还原为紧凑 UTF-8 JSON 后约 135 KB，超过旧客户端单条 96 KiB 字节限制。该检查在发出 HTTP 请求前就会返回普通错误 `invalid conversation turn`，因此没有模型 HTTP 诊断，也没有实际的复核否定意见。外层将它统一显示成 `grounding_review_failed`，造成误解。

同轮另有两个独立问题：

- `memory_read` 未命中记录时直接泄露 `sql: no rows in result set`，无法区分原始编号、记忆条目编号、范围或隔离状态。没有证据据此认定数据库损坏或历史消失。
- 多条旧分享的原生记录与记忆事件使用相同本地编号，但时间、发送者和服务器编号不一致，部分已有冲突记录。这会使保存来源校验不能通过；外层仍笼统显示识别服务失败。同轮存在正常完成的本地识别任务，因此不能将这些失败归因为识别服务整体不可用，也没有证据证明是视频无人声。
- 一段已读音轨与容器时长相差约四分之一毫秒，旧循环仍尝试继续读取尾部，并返回不一致的完成状态。

所有实际消息、来源编号和快照仅用于本机只读核对，未写入仓库。现存来源冲突不在本轮中强行覆盖、合并或删除。

## 行为调整

用户要求以明确的群成员身份和上下文解决对象问题，减少重复模型调用。`companion.grounding.enabled` 改为显式选择，缺省关闭；管理页“思考与回复”中可选择“额外模型复核”，旁边说明增加用量和等待时间。旧配置只有复核预算而未写入 `enabled=true` 时，不再自动追加模型核验或编辑。

关闭后仍执行程序的来源身份、会话授权、对象、版本、更正/遗忘及投递检查；这些检查不依赖第二次模型调用。回复、进度、显式发送使用同一配置，不能在其他路径悄悄追加群聊模型改稿。原有可选复核实现保留，不宣称程序校验能理解任意自然语言中的全部事实与隐私语义。

API `role` 继续表示 user/assistant/tool 等协议角色；微信身份由每条记录的发送者 ID、来源、引用对象、受话者和媒体上传者字段表示，昵称不作为身份。无法把每个微信 ID 直接改写成 API role。

可选复核的单条传输保护独立于普通短聊天，允许完整结构化证据在 1 MiB 单条、2 MiB 总输入范围内传输；这只是本地资源保护，不代表模型 Token 窗口。另核验管理员配置的窗口与输出预留，超限不截断正文。传输超限返回输入大小、限制、未调用 API 的阶段，来源冲突也使用独立诊断。

音轨错误区分来源未核验、插件结果未核验、后端资源不可用与识别未完成；保留“未识别到可转写语音”的正常结果，不把它变成服务失败。已读音轨结尾与请求终点不足 50 ms 的舍入差不再产生额外识别，实际结束位置、提前结束标记及容差仍返回。

## 验证范围

使用合成来源和本地模拟 HTTP 验证：默认回复不调用额外模型，但失效来源仍不能发送；可选复核模式保留旧测试；135 KB 结构化输入完整到达模拟端；超出保护范围不发 HTTP 并返回具体诊断；无语音状态不变成识别服务错误；不存在的记忆来源不再返回原始 SQL 错误。

本轮不新增真实模型测试或微信测试发送，不重新生成八条视频总结。默认模式会减少额外复核调用，但没有以实际付费调用估计账单节省比例。原始资料中的来源碰撞仍需按权威身份独立修复，关闭模型复核不能使错误来源变成有效来源，也不能证明八条视频任务已完成。
