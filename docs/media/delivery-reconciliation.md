# 附件投递与核对

同一个素材、来源、目标、格式和请求者的未完成投递复用原批次。更改调用的 `request_key` 或开始新一轮对话不会再创建同一附件的并行队列；已完成批次只在同一请求身份下复用，新的明确发送请求可以再次发送。创建及查重由同一个锁串行处理，返回原批次 `operation_id`，调用账本编号另存 `invocation_operation_id`。

共享 `AGENTS.md` 在保留主人备注的基础上合并“投递先核查，续办原批次”规范：先查真实目标记录和原任务，修复后续办；不换素材副本、任务或 key 反复排队，不重发已接受分段。`wechat_send_media` 的稳定 key 与 `wechat_delivery_retry` 的恢复调用 key 用途不同。

待核对记录保留原任务身份，并继续只读查询回执。`reconcile_after` 保存带随机性的重试退避时间，`next` 单独安排状态查询。旧版本将两者合并造成长时间看不到迟到回执，加载时迁移，保留原退避截止时间。实际上传中的任务仍串行；同批未确认分段仍阻止下一段，无关旧未知回执不再阻塞其他请求。未启动的主动分享让位于用户明确请求。

核对或续办失败记录原生原因，创建一次私聊排障任务，而非永远只显示“等待核对”。来自普通成员或自主冲浪的报告不继承主人执行身份。原发送器仍按授权和取消状态独立恢复，不把私聊报告当作管理员授权。

原生层保留同一加密计划、客户端消息身份和已接受回执。历史版本的 `media_processing_failed` 只有同时具备 `voice_handshake_before_submission` 阶段证据时，才允许核对后恢复；其他处理错误仍需排障。核对失败不触发写操作，聊天中的排队记忆不算送达证据。

重复历史批次可在确认尚未提交后由运维合并，保存 `superseded_by`，保留原记录、停止恢复重复队列并解除旧任务绑定。运行中的原生任务不靠修改状态强行取消。

回归覆盖：更换 key/消息身份仍复用未完成批次、合并批次重启不恢复、工作规范幂等合并、未知冲浪不阻塞用户任务、同批顺序、核对失败只创建一份报告、随机退避中发现迟到回执，以及报告不提升普通成员权限。真实微信接受和手机播放仍需分别验证；状态页不得把前者称为后者。
