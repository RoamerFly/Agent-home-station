# 微信 Bot 与工作站微信应用的实现对比

参考基线：`4e230477ebe42cdb16adba87ae7c19055c93b2dc`。

这次迁移把旧版微信 Bot 的控制台体验放进工作站的微信应用入口。旧版的消息收发、模型调用、会话记忆和发送回执仍是行为基线；工作站只增加应用生命周期、按连接授权、执行记录和 Windows 进程托管。

| 能力 | 旧版微信 Bot | 当前工作站微信应用 | 迁移结论 |
| --- | --- | --- | --- |
| 微信连接 | `linuxnative` 直接维护连接 | 微信连接适配器负责登录资料、连接状态和 Windows `wx.exe` 生命周期 | 工作站托管外层，连接行为保持一致 |
| 消息读取 | `bot.Worker.Run` 轮询事件游标，首次启动跳过历史 | 工作站连接接口读取同一类事件，并记录按连接的执行回合 | 沿用旧 Worker 语义，新增可见回合记录 |
| 模型与角色 | DeepSeek 配置、角色和群规则在管理台保存 | 主模型在工作站公共设置，微信连接保存会话、回复范围和应用授权 | 应用页展示微信相关授权，公共模型仍由工作站统一管理 |
| 工具调用 | Worker 在回合内调用微信、联网和媒体工具 | 连接级工具受宿主授权、项目工具登记和任务来源约束 | 不改变工具结果，只增加来源与权限核对 |
| 发送消息 | 原生发送后记录服务端回执，未知结果不自动重复 | 发送账本绑定连接、任务和来源，支持逐回合回执与安全续办 | 保留旧回执边界，新增持久账本 |
| 执行过程 | 旧版活动日志显示事件 | 微信应用「执行回合」按消息卡片显示收到的内容、每一步处理和工具调用 | 旧版日志体验迁入应用内 |
| 配置入口 | 独立微信管理后台 | 应用中心选择微信后点击「进入应用」，使用账号、会话、规则、流程、回合、投递和任务分区 | 不再要求用户理解“详细配置”或迁移状态 |

## 代码边界

- 旧版核心仍在 `cmd/wechat-bot/main.go`、`internal/bot/*`、`internal/linuxnative/*` 和 `internal/admin/*`。当前 `internal/admin/manager.go` 仍通过 `bot.New(...)` 创建并运行 Worker，没有用工作站适配器替换核心收发逻辑。
- 工作站外层位于 `internal/station/*`、`internal/stationui/static/local-home.*` 和 `dev/windows-station/connected-apps/wechat/adapter/*`。它负责应用登记、连接授权、回合展示、投递账本和桌面进程生命周期。
- Connected App 的 `migration-pending`/`runtime_migration=pending` 是应用协议登记状态，不能代表旧 Bot Worker 不可用；本轮不把声明文件改成 `ready`，避免用 UI 文案掩盖尚未完成的独立适配器迁移。

## UI 迁移原则

微信应用的“进入应用”弹窗采用旧版 Whale Console 的深海蓝卡片、窄侧栏、细描边和权限滑块；工作站聊天、记忆、抖音和项目工具继续使用各自的工作站主题。这样旧微信 Bot 的账号、回复规则、执行回合和投递页面在视觉上保持连续，同时不会把抖音或公共工具误认为微信专属配置。
