# 项目评估与优化建议

评估日期：2026-10-25。范围为当前源代码、现有验收记录和本机管理端近期运行记录。本次只读检查运行服务，未修改机器人配置或触发微信测试。建议属于工程判断，不是线上成功率或安全认证。

## 总体结论

项目已经形成可用的个人微信 Agent 原型：微信后台收发、原生工具调用、联网、媒体缓存与转换、百炼语音、本地 YuE、异步续办和网页管理均已有实现或真实链路证据。下一阶段优先做架构收敛、任务状态统一和可靠性交付。

当前适合授权会话内的个人试用。长期无人值守、增加群数和开放服务器高权限之前，需要强化任务状态、存储维护、执行隔离与真实任务回归。

值得保留的基础：

- Go 后台与微信适配层分离；模型通过原生 function calling 操作真实工具。
- 工具权限与可信身份检查独立于模型文本；关键外部动作有操作台账和幂等记录。
- 收件箱、游标、媒体发送、记忆均有持久化，外部结果未知时保留待核对状态。
- 已有增量上下文压缩、最近媒体来源、原文件复用及异步音乐任务续办。
- 最近运行记录显示，引用歌曲语音后要求完整文件，执行了文件准备、发送和回执确认，再发送介绍文字。这证明已有链路能够完成相关交付；不代表所有场景都可靠。

## 优先级与优化方向

### P0-1：统一用户请求、工具执行、生成结果和最终交付状态

证据：`internal/admin/agent_control.go` 的 `finishAgentTask` 在 `MusicPrepared` 且本轮回复结束后，将任务设为 `completed`，说明文字则表示“已交给持久化发送队列”。真正的发送状态位于 `internal/bot/media_delivery.go` 和媒体介绍队列中。模型任务完成与用户交付完成语义不同。

建议：

1. 用 request_id → task_id → action_id → artifact_id → delivery_id 建立稳定关联。
2. 分离执行阶段与交付阶段。生成完成、素材就绪、交付排队、部分已接受、全部已接受、失败、未知均应能表达。
3. 用户请求完成由全部必需交付项确认决定；模型本轮结束只是一次决策结束。
4. 重启和重试继续同一逻辑动作，不能靠新的 TraceID 或新上传编号间接创建重复交付。
5. 按结果类型制定恢复方式：只读请求可有界重试；生成先查原任务；发送先查原回执；未知写操作保留核对。

验收：在生成完成、首段发送完成、文件提交后未收到响应等时刻中断重启，任务状态准确，已接受内容不重复发送，未完成内容可继续或明确待核对。

### P0-2：让模型掌握行为选择，收敛自然语言关键词纠正

证据：`internal/admin/music_policy.go` 中，`musicKindFromText` 会检查固定词，覆盖传入的 kind；`internal/companion/music_contract.go` 中仍有关键词快速判断，并对相关轮次调用模型核验承诺。

具体问题：例如“唱完把下载版也给我”，即使模型理解后选择 both，现有文件判断不认识“下载版”，仍可能返回 voice。时长正则只覆盖有限汉字数字，“一百二十秒”可能匹配尾部“十秒”，得到10秒。

建议：

- 由同一轮模型工具调用表达语义目标、时长、交付格式以及它基于哪条请求作出选择。
- 后台验证参数范围、权限、前置条件、来源和实际结果，不默认重新解释整句用户话。
- 将“默认完整分段语音”等偏好作为可被当前明确请求覆盖的默认值，区别于不可越过的权限。
- 用真实 action/task 记录判断是否已经执行；承诺核验作为过渡措施，避免每个音乐相关聊天都多一次核验调用。
- 复合需求表达为多个交付目标，允许唱歌与文件并存，不把格式切换一律理解为取消所有旧任务。

验收：同义表达、否定、修改需求、跨轮确认等真实模型场景通过；普通聊音乐不会创建歌曲；模型明确选择的合法格式不会被关键词意外覆盖。

### P0-3：建立可追溯的媒体与任务关联，减少指代漂移

证据：已有 `recentMediaFocus`、素材 hash、asset_id、source_url 和素材复用；但自动音乐续办主要传入任务标题、job_id、kind，再结合近期会话判断。上下文摘要仍由模型生成。

建议：

- 将原始请求、当前有效修订、发起人、原消息、引用消息、任务及交付目标存成结构化记录。
- 为媒体维护转换链：原始网页/视频 → 下载文件 → 提取音轨 → 语音分段 → 微信消息。
- 引用消息优先按消息编号精确定位素材，再按同一用户的活动任务和近期媒体解析指代。
- 旧话题明确有结束/被替代状态；不同用户的同时请求保持独立。
- 压缩摘要只负责背景和偏好；job_id、素材来源、发送回执等权威状态从记录查询，不让摘要成为事实来源。

验收：在动画视频、歌曲和旧铁路话题交错时，“把这个原文件发我”仍能定位引用的正确媒体；同群两人任务互不覆盖。

### P0-4：高权限工具独立执行边界

证据：`internal/agenthost/host.go` 明确 full 模式按管理端服务用户执行 Shell；授权目录限制文件工具与命令起始目录，不构成命令沙箱。可信用户及会话检查已有实现，应保留。

建议：

- 将可执行命令的服务与持有微信会话、服务商 Key 的管理进程分离。
- 按能力开放只读、文件创建、指定程序和完整 Shell，允许用户显式选择更高权限。
- 为执行服务限制身份、可见文件、凭据、网络和资源；高权限授权支持指定任务、有效期和撤销。
- 把“用户授予的权限”和网页/MCP/群聊文本内容分开；外部资料不能扩大授权。
- 同样审查 stdio MCP 子进程的环境与可见文件，避免默认继承不必要的凭据。

验收：执行器只能看到已授权的资源；关闭权限后后续动作立即被阻止；高权限操作有任务、身份与结果记录。

### P1-1：事务存储、归档与磁盘维护

证据：多个独立 JSON 文件分别维护任务、操作、素材、发送、记忆、日志。单文件采用临时文件与替换，不能自动提供跨文件事务。任务500条、操作2000条、发送1000条、素材1000项/512MiB等上限已有检查；达到上限时会拒绝新增。

建议：

- 将逻辑关联状态逐步迁移到事务型本地存储，媒体二进制仍按 hash 保存。
- 统一状态迁移和待发送事件提交，保留外部动作的幂等与未知结果语义。
- 对已终态记录归档；按引用关系回收未使用媒体，保留进行中、待核对、用户固定的原件。
- 建立版本迁移、备份与恢复检查；容量预警和清理结果可在管理页查看。

验收：完成存量导入、备份恢复和容量接近上限测试；不能通过随意清空台账换取继续运行。

### P1-2：插件契约与 MCP 生命周期

证据：API 插件已支持参数描述、媒体返回、异步轮询；`mcptools.go` 中 stdio 每个请求新启动进程并初始化，结束后关闭；HTTP 路径也每次初始化。

建议：

- 插件能力增加只读/副作用类型、幂等键语义、异步状态查询、取消、输出类型和权限需求。
- MCP 管理连接与进程生命周期，支持配置变更后重建、健康状态、退避重连和必要的会话隔离。
- 缓存工具 Schema，并在工具目录变化或配置变化时更新；权限始终逐次复核。
- 将音乐生成接入统一异步能力接口，减少 YuE 专用字段继续扩散到调度、决策和发送代码。
- 插件安装、工具发现、服务连通、实际调用、媒体可发送分别显示状态。

验收：具备会话内状态的测试 MCP 连续调用可保持状态；插件异常不会拖垮其他会话；取消与恢复有明确结果。

### P1-3：上下文预算与压缩质量

证据：已有最近消息限制与增量压缩；`MaxInputChars` 的计数使用序列化后的字节长度；摘要主要验证 JSON 语法与长度，未严格验证约定字段及媒体引用完整性。

建议：

- 将上下文按当前请求、活动任务、引用、近期对话、长期偏好、工具结果分配预算，避免历史聊天挤掉任务状态。
- 采用模型适配的 token 估算；准确区分字节、字符和 token。
- 为摘要定义严格结构，标明来源、更新时间与被纠正事实；关键 ID 与 URL 直接由记录回填。
- 在前台提供脱敏的“本轮实际上下文”和 token 构成查看，便于定位串台与费用来源。

验收：长聊压缩后仍保留当前任务和原素材引用；摘要失败有明确降级；压缩不会恢复已经取消的旧需求。

### P1-4：真实任务回归与可观测性

证据：仓库已有较多测试和故障注入记录，最近全量 Go 测试通过；最近音乐语义验证覆盖3个生成指令及承诺判断，生成服务和微信传输为模拟，不能等同于所有真实模型多轮行为通过。

建议：

- 将实际故障转为固定场景集：承诺未执行、引用错位、换文件、换歌、多人并发、中断、重启、部分回执和工具网络失败。
- 为每轮记录 request/task/action/delivery 关联，合并为可展开任务时间线。
- 区分模型决策错误、工具参数错误、网络/来源限制、媒体处理错误、微信提交错误和未知回执。
- 统计完成率、部分成功率、重复发送、取消响应、端到端耗时、每任务费用，并标明分母和观察窗口。
- 将单元、故障注入、真实模型选参、真实工具执行、微信接受、手机可播放分层验收。

验收：每项历史事故有可重复场景；从一条用户消息可查完整因果链；看到失败即可定位所属阶段。

### P2：交付、配置与管理页面

证据：当前目录和父目录不是 Git 仓库。`FEATURES.md` 顶部仍为0.8.3，而代码状态接口为0.8.4；文档仍有“未接入收到语音转录”“没有恢复生成任务调度器”等与现有实现冲突的旧描述。

建议：

- 建立版本管理、受控变更、可重复验证和发布清单；私有密钥、账号会话和媒体继续排除在版本管理之外。
- 从能力注册表生成前端配置说明、工具目录及功能状态，减少文档和代码手工同步。
- 设置页按角色、社交偏好、能力权限、运行预算、故障恢复分组；常用项与高级项分层，跨页不重复存同一设置。
- 增加任务中心、媒体来源详情和可执行的失败诊断；保留日志阅读位置。
- Linux 部署前区分管理服务、微信接入、本地/GPU生成服务各自依赖与健康状态；本阶段继续不导出镜像。

## 建议执行顺序

1. 统一请求、任务与交付状态，先确保能解释每次失败和部分成功。
2. 把需求修订与媒体转换链结构化，然后收敛关键词行为覆盖。
3. 将异步生成与 MCP 插件纳入共同生命周期，补充存储归档与恢复。
4. 完成代表性多轮回归和高权限执行隔离，再扩大长期运行与账号自主能力。

## 主要依据

- `internal/admin/music_policy.go`、`internal/companion/music_contract.go`：语义与行为纠正。
- `internal/admin/agent_control.go`、`internal/admin/yue.go`：任务与音乐续办。
- `internal/bot/media_delivery.go`、`internal/bot/media_reply.go`：发送与回执。
- `internal/companion/context.go`、`internal/admin/media_assets.go`：压缩与素材关联。
- `internal/mcptools/mcptools.go`、`internal/plugins/plugins.go`：MCP与插件契约。
- `internal/agenthost/host.go`：服务器能力边界。
- `research/evidence/music-delivery-go-tests.log`、`music-semantic-validation.log`、`music-semantic-intent-live.json`：已有验证范围。

以上建议不要求整体重写。优先在现有链路之上统一状态、关联和接口，迁移期间保留现有真实接入与可验证行为。
